Введение
Учебный процесс всё чаще опирается на цифровые материалы, электронные курсы, презентации, личные кабинеты и сетевые сервисы университета. Студенту во время самоподготовки может понадобиться ноутбук, планшет или портативное зарядное устройство. Такая потребность возникает в читальном зале, аудитории самоподготовки, коворкинге, на кафедре или рядом с ответственным сотрудником, который ведёт выдачу оборудования.
При ручном учёте появляются типичные сложности. Сотруднику приходится отдельно проверять наличие свободных устройств, фиксировать выдачу, запоминать место хранения и контролировать возврат. Часть сведений может храниться в таблицах, журналах или устных договорённостях. Из-за этого становится труднее быстро определить, какое оборудование доступно студентам, где оно находится и кто пользуется им в данный момент.
Для решения этой задачи разрабатывается веб-приложение, предназначенное для ведения реестра оборудования, используемого при организации самоподготовки студентов ДГТУ. В системе учитываются разные виды устройств: ноутбуки, планшеты и портативные зарядные устройства. Пользователь просматривает доступное оборудование, выбирает подходящий вариант и оформляет заявку на выдачу. Ответственный сотрудник проверяет заявку, подтверждает выдачу, меняет статус устройства и после возврата фиксирует завершение использования.
Разрабатываемое приложение должно поддерживать авторизацию пользователей, просмотр доступного оборудования, оформление заявки, учёт мест хранения, контроль текущего статуса устройства и ведение истории выдач. Для администратора предусматриваются функции управления пользователями, категориями оборудования, отдельными устройствами, местами хранения и заявками. Такой набор функций помогает перейти от разрозненного учёта к единой базе данных, где сведения об оборудовании обновляются после каждой операции.
Целью дипломной работы является проектирование и разработка веб-приложения для ведения реестра оборудования, используемого для организации процесса самоподготовки студентов ДГТУ. Приложение должно автоматизировать выдачу, возврат и учёт оборудования, а также упростить работу ответственных сотрудников с данными о доступных устройствах.
Для достижения поставленной цели необходимо решить следующие задачи:
рассмотреть предметную область учёта оборудования, применяемого для самоподготовки студентов;
изучить особенности выдачи устройств в образовательной организации;
определить основные функции разрабатываемой системы;
выделить роли пользователей и описать действия каждой роли;
разработать диаграммы, отражающие процессы работы приложения;
спроектировать структуру базы данных для хранения сведений об оборудовании, заявках и пользователях;
описать программную реализацию основных разделов веб-приложения;
проверить работу системы на примере выдачи и возврата оборудования.
Разработанное веб-приложение может применяться в образовательной организации для упорядоченного учёта устройств, которые используются студентами во время самоподготовки. Система помогает ответственному сотруднику быстрее находить сведения о наличии оборудования, контролировать его местонахождение и видеть историю использования. Для студентов приложение делает процесс получения нужного устройства понятнее: доступное оборудование отображается в одном месте, а заявка оформляется через веб-интерфейс.

1.2 Характеристика объекта автоматизации
Объектом автоматизации является процесс учёта и выдачи оборудования, используемого для организации самоподготовки студентов ДГТУ. К такому оборудованию относятся ноутбуки, планшеты и портативные зарядные устройства. Устройства могут храниться в читальном зале, коворкинге, аудитории самоподготовки, на кафедре или у ответственного сотрудника, который контролирует их состояние и передачу студентам.
При ручной организации этого процесса сотруднику приходится отдельно вести сведения о наличии оборудования, фиксировать выдачу, отмечать возврат и следить за состоянием каждого устройства. Такой порядок неудобен при регулярных обращениях студентов. Если данные хранятся в разных таблицах или бумажных журналах, становится сложнее быстро определить, какое оборудование свободно, где оно находится и кто пользовался им ранее.
Разрабатываемая система представляет собой веб-приложение, которое объединяет сведения об оборудовании в едином реестре. В нём хранятся данные о типе устройства, его названии, инвентарном номере, месте хранения, текущем статусе и истории использования. Благодаря этому ответственный сотрудник получает более точную картину по оборудованию, а студент может заранее посмотреть доступные устройства через веб-интерфейс.
Пользовательский раздел предназначен для взаимодействия студента с системой. После регистрации и входа в личный кабинет студент просматривает доступное оборудование, выбирает нужное устройство и оформляет заявку на выдачу. В заявке фиксируются сведения о пользователе, выбранном оборудовании, предполагаемом месте получения и текущем статусе обращения. Такой порядок делает процесс получения устройства более понятным, поскольку основные действия выполняются через приложение.
Раздел ответственного сотрудника используется для обработки заявок и контроля оборудования. Сотрудник просматривает поступившие обращения, проверяет наличие устройства, подтверждает выдачу и меняет его статус. После возврата он фиксирует завершение использования, при необходимости отмечает неисправность или переводит устройство обратно в доступное состояние. Этот раздел помогает избежать путаницы при передаче оборудования между студентами.
Административная часть разрабатываемой системы нужна для управления справочными данными и контроля работы приложения. Через неё можно добавлять новые устройства, редактировать сведения о местах хранения, управлять пользователями, просматривать историю заявок и отслеживать состояние оборудования. Администратор видит, какие устройства доступны, какие находятся у студентов, какие требуют проверки или ремонта.
Отдельное значение имеет разграничение доступа. Студент работает только с личным кабинетом и заявками на оборудование. Ответственный сотрудник получает доступ к обработке выдачи и возврата. Администратор управляет всей информацией, связанной с пользователями, устройствами и местами хранения. Такой порядок снижает риск случайного изменения данных и помогает сохранить корректность сведений в системе.
Техническая часть включает базу данных, серверную логику веб-приложения и пользовательский интерфейс. База данных хранит сведения о пользователях, оборудовании, категориях, местах хранения, заявках и статусах. Серверная часть обрабатывает запросы, проверяет права доступа, меняет состояние устройств и передаёт пользователю актуальную информацию. Интерфейс приложения обеспечивает работу со всеми основными разделами без обращения к отдельным файлам или бумажным журналам.
Автоматизация данного процесса имеет практическое значение для образовательной организации. Студенты получают более простой доступ к оборудованию, которое может понадобиться во время самоподготовки. Ответственные сотрудники быстрее находят сведения о наличии устройств и истории их использования. Для университета такая система упорядочивает внутренний учёт оборудования и помогает контролировать его движение между местами хранения и пользователями.

1.4Постановка задачи
Целью данной выпускной квалификационной работы является разработка веб-приложения для ведения реестра оборудования, используемого для организации процесса самоподготовки студентов ДГТУ. Разрабатываемая система должна упростить учёт ноутбуков, планшетов и портативных зарядных устройств, обеспечить оформление заявок на выдачу, контроль текущего состояния оборудования и фиксацию возврата после завершения использования.
Необходимость разработки связана с тем, что во время самоподготовки студентам часто требуется доступ к техническим средствам. При работе с электронными учебными материалами, личным кабинетом, документами и образовательными сервисами может понадобиться ноутбук или планшет. В течение учебного дня также возникает потребность в портативном зарядном устройстве. Если сведения об оборудовании хранятся в отдельных таблицах, бумажных журналах или у разных сотрудников, поиск свободного устройства занимает больше времени. Кроме того, усложняется контроль за тем, где находится оборудование, и кто пользовался им ранее.
Разрабатываемое веб-приложение должно объединить сведения об оборудовании в едином реестре. В системе необходимо хранить данные о типе устройства, названии, инвентарном номере, месте хранения, текущем статусе и истории использования. Студент должен иметь возможность заранее посмотреть доступные устройства и оформить заявку на выдачу. Ответственный сотрудник проверяет заявку, подтверждает передачу оборудования, меняет его статус и после возврата фиксирует завершение использования.
Для достижения поставленной цели необходимо решить следующие задачи:
Исследовать предметную область учёта и выдачи оборудования, используемого при самоподготовке студентов.
Провести сравнительный анализ аналогичных решений.
Определить требования к разрабатываемой системе.
Выбрать средства разработки веб-приложения.
Выполнить проектирование структуры приложения.
Смоделировать базу данных.
Разработать механизм подачи заявки, выдачи, возврата и контроля состояния оборудования.
Создать интерфейс для студента, ответственного сотрудника и администратора.
Описать порядок работы созданного веб-приложения.
При постановке задачи требования к системе разделяются на функциональные и нефункциональные. Функциональные требования определяют действия, которые должны быть доступны пользователям приложения. Нефункциональные требования описывают условия работы системы, требования к удобству интерфейса, защите данных, надёжности хранения сведений и дальнейшему сопровождению проекта.
Для студента система должна предусматривать регистрацию, авторизацию и работу с личным кабинетом. После входа в приложение студент получает доступ к списку оборудования, которое может использоваться для самоподготовки. В карточке устройства должны отображаться его тип, название, место хранения и текущий статус. Если оборудование доступно, студент оформляет заявку на выдачу и ожидает обработки со стороны ответственного сотрудника.
Во время работы с заявкой студент должен видеть её состояние. В интерфейсе отображается, отправлена ли заявка, подтверждена ли выдача, находится ли оборудование у пользователя или уже возвращено. В личном кабинете также должна быть доступна история обращений. Это позволит студенту просматривать ранее использованные устройства и отслеживать завершённые операции.
Для ответственного сотрудника требуется отдельный раздел работы с заявками. Через него сотрудник просматривает поступившие обращения, проверяет наличие оборудования и подтверждает выдачу. После передачи устройства студенту система должна менять статус оборудования на занятое. При возврате сотрудник фиксирует завершение использования, после чего устройство снова становится доступным либо переводится в статус неисправного, если требуется проверка или ремонт.
Работа ответственного сотрудника также связана с контролем места хранения. Оборудование может находиться на кафедре, в читальном зале, коворкинге, аудитории самоподготовки или у конкретного сотрудника. Для каждого устройства необходимо сохранять сведения о его текущем размещении. Это позволит быстрее находить нужное оборудование и снизить риск потери данных о его перемещении.
Для администратора разрабатываемая система должна включать раздел управления. Администратор получает доступ к списку пользователей, категориям оборудования, местам хранения, заявкам и истории использования. Через административный раздел он добавляет новые устройства, редактирует сведения об уже внесённом оборудовании, меняет данные о местах хранения и при необходимости корректирует статусы.
Отдельно выделяются требования к самой системе. Веб-приложение должно хранить сведения о пользователях, ролях, оборудовании, категориях, местах хранения, заявках и статусах. При подтверждении выдачи система фиксирует дату и время передачи устройства студенту. После возврата сохраняется дата завершения операции. На основании этих данных формируется история использования оборудования.
К нефункциональным требованиям относится понятная структура интерфейса. Студент должен быстро находить доступное оборудование и оформлять заявку без обращения к сторонним таблицам или бумажным журналам. Страницы приложения должны корректно отображаться на компьютере и мобильном телефоне, поскольку часть обращений может оформляться со смартфона.
Разрабатываемая система должна обеспечивать защиту пользовательских данных. Доступ к личному кабинету открывается после авторизации. Разделы ответственного сотрудника и администратора должны быть закрыты для обычных пользователей. При работе с базой данных требуется сохранять корректные сведения о заявках, устройствах, местах хранения и статусах оборудования.
Отдельное внимание уделяется точной фиксации операций [6]. Приложение должно сохранять начало использования оборудования и его завершение, менять статусы устройств после выдачи или возврата, не терять сведения при обновлении данных. Для дальнейшей доработки проекта код и структура базы данных должны оставаться понятными для сопровождения.
Работа студента с разрабатываемой системой начинается с регистрации или входа в личный кабинет [2]. После авторизации студент выбирает тип оборудования, просматривает доступные устройства и оформляет заявку. Ответственный сотрудник проверяет обращение и подтверждает выдачу. После передачи устройства система фиксирует начало использования. При возврате сотрудник завершает операцию, а сведения сохраняются в истории.
Администратор использует систему для общего контроля. Он просматривает пользователей, оборудование, места хранения и заявки. При необходимости администратор изменяет сведения об устройствах, добавляет новые категории, проверяет историю операций и отслеживает проблемные ситуации. К таким ситуациям относятся потеря устройства, неисправность, несвоевременный возврат или ошибочно установленный статус.
Разрабатываемое веб-приложение должно упорядочить процесс учёта оборудования, используемого при самоподготовке студентов ДГТУ. Основное внимание при разработке уделяется удобству работы с реестром, точной фиксации выдачи и возврата, защите данных и возможности администрирования оборудования. Логика временной выдачи портативных зарядных устройств сохраняется в системе как один из сценариев, но теперь она входит в общий процесс управления оборудованием.
2. Проектирование веб-приложения для управления чем-ля аренды зарядных устройств
Проектирование информационной системы является важным этапом разработки веб-приложения для ведения реестра оборудования, используемого при организации самоподготовки студентов ДГТУ. На данном этапе определяется общая структура приложения, состав его функций и порядок взаимодействия пользователей с системой. Разрабатываемое приложение должно обеспечивать учёт оборудования, оформление заявок на выдачу, контроль текущего состояния устройств и фиксацию возврата после завершения использования.
Структурный анализ включает построение функциональной модели, диаграммы потоков данных и диаграммы прецедентов. Эти диаграммы отражают основные процессы работы приложения: просмотр доступного оборудования, подачу заявки студентом, подтверждение выдачи ответственным сотрудником, изменение статуса устройства и управление реестром со стороны администратора.
2.1. Моделирование бизнес-процессов веб-приложения
Структурный анализ применяется при проектировании разрабатываемой системы для описания её состава, функций и связей между отдельными частями. Такой подход помогает рассмотреть работу веб-приложения поэтапно: от действий студента при выборе оборудования до обработки заявки ответственным сотрудником и сохранения данных в реестре. На этом этапе определяются основные процессы, участники системы, потоки информации и результаты выполнения операций.
Полученное описание используется при построении диаграмм, разработке базы данных и дальнейшей программной реализации приложения. За счёт этого можно заранее определить, какие сведения должны передаваться между пользовательским интерфейсом, серверной частью и базой данных, а также какие изменения происходят в системе после выдачи или возврата ноутбука, планшета либо портативного зарядного устройства.
Диаграмма прецендентов
Диаграмма прецедентов представляет собой графическое описание функциональных возможностей разрабатываемой системы. Она помогает определить основные сценарии взаимодействия пользователей с веб-приложением и показать, какие действия доступны каждому участнику системы [14]. С помощью данной диаграммы можно отразить роли пользователей, их права доступа и функции, которые должны быть реализованы при разработке приложения.
На рисунке 3.1 представлена диаграмма прецедентов веб-приложения для ведения реестра оборудования, используемого для организации процесса самоподготовки студентов ДГТУ.
Рисунок 3.1 – Диаграмма прецедентов
В диаграмме выделены три основных актора: пользователь, сотрудник выдачи и администратор. Пользователь работает с веб-приложением для регистрации, авторизации, просмотра доступного оборудования, оформления заявки на выдачу, отслеживания её статуса и возврата оборудования. Сотрудник выдачи обрабатывает заявки, подтверждает выдачу, фиксирует возврат, изменяет статус оборудования и отмечает неисправности. Администратор выполняет действия, связанные с управлением пользователями, категориями оборудования, местами хранения, заявками и контролем состояния устройств [8].
Прецеденты для пользователя:
– регистрация – создание учётной записи пользователя для получения доступа к основным функциям веб-приложения
– авторизация – вход пользователя в систему с использованием учётных данных. После авторизации пользователь получает доступ к личному кабинету, просмотру оборудования и оформлению заявки на выдачу
– просмотр доступного оборудования – получение списка устройств, которые могут быть использованы для самоподготовки. В данный список могут входить ноутбуки, планшеты и портативные зарядные устройства
– просмотр карточки оборудования – просмотр сведений о выбранном устройстве, включая его название, тип, место хранения и текущий статус
– оформление заявки на выдачу – создание заявки на получение оборудования во временное пользование
– выбор типа оборудования – указание категории устройства при оформлении заявки. Пользователь может выбрать ноутбук, планшет или портативное зарядное устройство
– выбор места получения – выбор места, где пользователь планирует получить оборудование. В качестве места получения может выступать кафедра, читальный зал, коворкинг, аудитория самоподготовки или сотрудник выдачи
– просмотр статуса заявки – получение информации о текущем состоянии заявки. Пользователь может увидеть, находится ли заявка на рассмотрении, подтверждена ли она, выполнена или завершена после возврата
– просмотр истории заявок – получение сведений о ранее оформленных заявках и использованном оборудовании
– возврат оборудования – завершение использования устройства и передача оборудования сотруднику выдачи
– редактирование профиля – изменение личных данных пользователя, указанных при регистрации
Прецеденты для сотрудника выдачи:
– авторизация – вход сотрудника выдачи в систему для доступа к разделу обработки заявок и управления статусами оборудования
– просмотр заявок на выдачу – получение списка заявок, оформленных пользователями
– подтверждение выдачи оборудования – проверка заявки и подтверждение возможности передачи оборудования пользователю
– фиксация выдачи оборудования – сохранение сведений о передаче устройства пользователю. После выполнения данного действия статус оборудования изменяется
– фиксация возврата оборудования – сохранение сведений о возврате устройства после завершения использования
– изменение статуса оборудования – изменение состояния устройства в системе. Оборудование может быть доступно, выдано, возвращено, неисправно или находиться на проверке
– отметка неисправности оборудования – фиксация проблемы с устройством после проверки или возврата
– просмотр оборудования по месту хранения – получение списка устройств, закреплённых за определённым местом хранения
Прецеденты для администратора:
– регистрация – создание или первичная настройка учётной записи администратора для дальнейшего доступа к системе
– авторизация – вход администратора в систему для работы с административным разделом
– управление пользователями – просмотр учётных записей, изменение данных пользователей и контроль их ролей в системе
– управление категориями оборудования – добавление, редактирование и удаление категорий устройств
– управление оборудованием – добавление новых устройств в реестр, изменение сведений об оборудовании и удаление неактуальных записей
– управление местами хранения – ведение списка мест, где размещается оборудование
– просмотр всех заявок – получение общего списка заявок, созданных пользователями
– просмотр истории использования – просмотр сведений о выдаче, возврате и движении оборудования
– контроль состояния оборудования – отслеживание текущего состояния устройств, их доступности и исправности
– просмотр проблемных ситуаций – просмотр случаев, связанных с неисправностью оборудования, несвоевременным возвратом, ошибочным статусом или потерей устройства
На диаграмме также показаны связи включения. При оформлении заявки пользователь выбирает тип оборудования и место получения. Эти действия входят в общий процесс создания заявки, поскольку без них система не сможет определить, какое устройство требуется пользователю и где его нужно получить.
Отдельная связь связана с изменением статуса оборудования. Данный прецедент используется при подтверждении выдачи, фиксации выдачи, фиксации возврата и отметке неисправности. После каждого такого действия сведения в реестре должны обновляться, чтобы в системе отображалось актуальное состояние оборудования.
Диаграмма прецедентов показывает распределение функций между участниками разрабатываемой системы [6]. Пользователь выполняет действия, связанные с получением оборудования для самоподготовки. Сотрудник выдачи отвечает за фактическую передачу устройств, возврат и изменение их состояния. Администратор управляет справочными данными, контролирует заявки и следит за состоянием оборудования. Такое разделение ролей помогает определить функциональные требования к веб-приложению и подготовить основу для дальнейшего проектирования.
Диаграмма потоков данных
Диаграмма потоков данных DFD используется для описания движения информации между внешними участниками, процессами системы и хранилищем данных. Такая диаграмма помогает показать, какие сведения поступают в веб-приложение, где они обрабатываются и какие результаты возвращаются пользователям системы [3].
Для разрабатываемого веб-приложения DFD-модель показывает работу с данными о пользователях, оборудовании, заявках, статусах и местах хранения. С её помощью можно проследить, как пользователь оформляет заявку на выдачу оборудования, как сотрудник выдачи обрабатывает обращение, а администратор получает сведения для контроля и управления реестром [2].
На рисунке 3.2 представлена контекстная диаграмма потоков данных нулевого уровня.
Рисунок 3.2 – DFD-диаграмма нулевого уровня
На диаграмме нулевого уровня веб-приложение представлено как единый процесс. Система взаимодействует с тремя внешними сущностями: пользователем, сотрудником выдачи и администратором.
Пользователь передаёт в систему данные регистрации и авторизации, запрос на просмотр оборудования, данные заявки на выдачу, запрос статуса и истории заявок, сведения о возврате оборудования и данные профиля. В ответ он получает результат регистрации или авторизации, сведения о доступном оборудовании, результат обработки заявки, текущий статус обращения, историю заявок, подтверждение возврата и обновлённые данные профиля.
Сотрудник выдачи работает с системой через операции, связанные с обработкой заявок. В веб-приложение поступают запросы на обработку обращений, данные выдачи и возврата оборудования, сведения об изменении статуса устройства и запросы по оборудованию, закреплённому за местом хранения. В ответ система возвращает сведения о заявках на выдачу, результат обработки выдачи и возврата, обновлённые статусы оборудования и данные об оборудовании по месту хранения.
Администратор передаёт запросы на управление пользователями, оборудованием, категориями и местами хранения. Отдельно он запрашивает отчётные данные, сведения о заявках, истории использования, состоянии оборудования и проблемных ситуациях. Система возвращает администратору данные пользователей, сведения об оборудовании, категориях и местах хранения, результат изменения данных, историю использования и информацию для контроля состояния оборудования.
Контекстная диаграмма показывает внешние границы разрабатываемой системы. На этом уровне не раскрывается внутренняя структура приложения, но уже видно, какие участники работают с системой и какие группы данных проходят через веб-приложение.
Рисунок 3.3 – DFD-диаграмма первого уровня
DFD-диаграмма первого уровня раскрывает внутреннюю структуру веб-приложения. На ней показаны основные процессы обработки данных и база данных, которая используется как центральное хранилище сведений о пользователях, оборудовании, категориях, местах хранения, заявках, статусах и истории использования.
В системе выделен процесс авторизации и регистрации. Через него проходят данные входа в систему и регистрационные сведения. Данный процесс связан не только с пользователем, но и с сотрудником выдачи и администратором, поскольку доступ к рабочим разделам приложения должен предоставляться после проверки учётных данных. После обращения к базе данных система возвращает результат регистрации или авторизации.
Процесс просмотра оборудования отвечает за получение сведений о доступных устройствах. Пользователь отправляет запрос на просмотр оборудования, а система получает из базы данных сведения о ноутбуках, планшетах, портативных зарядных устройствах, их категориях, статусах и местах хранения. После обработки пользователь видит список доступного оборудования.
Оформление заявки на выдачу связано с созданием обращения на получение устройства. Пользователь передаёт данные заявки, а система сохраняет их в базе данных и формирует результат обработки. После этого заявка получает статус, по которому можно отслеживать её дальнейшее состояние.
Для просмотра текущих и прошлых обращений используется процесс просмотра заявок и истории. Пользователь запрашивает статус заявки или историю своих обращений. Система обращается к базе данных и возвращает сведения о заявках, их состоянии и ранее использованном оборудовании.
Возврат оборудования выделен в отдельный процесс, поскольку после завершения использования устройства необходимо обновить данные в реестре. В систему поступают сведения о возврате, затем меняется статус оборудования и связанной заявки. Если устройство возвращено и не требует проверки, оно снова может отображаться как доступное.
Редактирование профиля связано с изменением личных данных пользователя. Новые сведения передаются в систему, сохраняются в базе данных, после чего пользователь получает обновлённые данные профиля.
Сотрудник выдачи работает через процесс обработки заявок. В этом процессе выполняется просмотр обращений, подтверждение выдачи, фиксация выдачи и возврата, изменение статуса оборудования. При необходимости сотрудник передаёт сведения о неисправности устройства. Все изменения сохраняются в базе данных, чтобы состояние реестра оставалось актуальным.
Административная часть представлена процессом управления справочниками. Через него администратор работает с данными пользователей, оборудования, категорий и мест хранения. Эти сведения используются в других процессах системы, поэтому их корректность влияет на оформление заявок, отображение доступного оборудования и обработку выдачи.
Отдельный процесс связан с отчётами и контролем. Администратор запрашивает отчётные данные, историю использования, состояние оборудования и сведения о проблемных ситуациях. Система получает необходимые данные из базы и возвращает информацию, по которой можно контролировать движение оборудования и выявлять спорные случаи.
DFD-диаграмма первого уровня показывает, что разрабатываемая система состоит из нескольких связанных процессов. Пользовательские действия охватывают регистрацию, вход, просмотр оборудования, оформление заявки, просмотр истории, возврат оборудования и редактирование профиля. Сотрудник выдачи отвечает за обработку заявок и изменение статусов устройств. Администратор управляет справочными данными и получает сведения для контроля.
База данных используется как общее хранилище информации. В ней сохраняются данные пользователей, роли, сведения об оборудовании, категории, места хранения, заявки, статусы, история выдачи и возврата. Такая структура помогает связать отдельные процессы приложения и обеспечить обновление данных после каждого действия.
Диаграмма потоков данных показывает, как сведения проходят через веб-приложение и какие результаты получают участники системы. Полученная модель используется при дальнейшем проектировании базы данных, бизнес-логики и пользовательского интерфейса.
Диаграмма функциональной модели
Методология IDEF0 применяется для описания работы информационной системы через набор функциональных блоков. Такая модель показывает, какие данные поступают в систему, какие правила влияют на выполнение процессов, кто участвует в работе приложения и какие результаты формируются после обработки информации.
Для разрабатываемого веб-приложения функциональная модель помогает показать общую логику учёта оборудования, используемого для самоподготовки студентов ДГТУ. В отличие от диаграммы потоков данных, где основное внимание уделяется движению информации, IDEF0 отражает назначение процессов и связь между входными данными, управляющими документами, участниками системы и выходными результатами [6].
На рисунке 3.4 представлена контекстная диаграмма функциональной модели. Основной процесс обозначен как «Функционирование веб-приложения для ведения реестра оборудования, используемого для самоподготовки студентов ДГТУ». Он отражает работу системы в целом: от поступления данных о пользователе и оборудовании до формирования заявки, обновления статуса устройства и получения отчётов.
Рисунок 3.4 – Контекстная диаграмма
На вход разрабатываемой системы поступают данные пользователя, сведения об оборудовании, данные заявки и данные возврата. Данные пользователя применяются при регистрации, авторизации и работе с профилем. Сведения об оборудовании включают информацию о ноутбуках, планшетах и портативных зарядных устройствах, их состоянии, категории и месте хранения. Данные заявки нужны для оформления выдачи, а данные возврата используются после завершения работы с оборудованием.
Управляющими воздействиями выступают пользовательское соглашение, Федеральный закон «О персональных данных» и регламент выдачи и возврата оборудования. Эти элементы задают правила работы системы: порядок обработки персональных данных, условия использования веб-приложения, права пользователя и внутренний порядок передачи оборудования студентам.
Механизмами выполнения процесса являются пользователь, сотрудник выдачи и администратор. Пользователь просматривает доступное оборудование, оформляет заявку и возвращает устройство после использования. Сотрудник выдачи проверяет обращения, подтверждает выдачу, фиксирует возврат и изменяет статус оборудования. Администратор ведёт справочные данные, работает с пользователями, категориями, местами хранения и получает сведения для контроля.
На выходе формируются оформленная заявка, актуальный статус оборудования, история использования и отчёты по оборудованию. Эти результаты показывают, что система не просто хранит перечень устройств, а фиксирует полный цикл работы с ними: выбор, заявку, выдачу, возврат и последующее обновление данных в реестре.

Рисунок 3.5 – Декомпозиция контекстной диаграммы
В декомпозиции выделены следующие функциональные блоки:
– авторизация и регистрация – процесс, отвечающий за проверку учётных данных и предоставление доступа к системе. Через него пользователь, сотрудник выдачи и администратор получают доступ к тем разделам, которые соответствуют их роли. При выполнении процесса учитываются пользовательское соглашение и требования законодательства о персональных данных;
– управление оборудованием и местами хранения – процесс, связанный с ведением сведений о ноутбуках, планшетах, портативных зарядных устройствах, категориях, статусах и местах размещения. В этот блок поступают сведения об оборудовании, после чего формируются данные о доступных устройствах для просмотра и последующего оформления заявки;
– просмотр доступного оборудования и карточки оборудования – процесс, через который пользователь получает информацию о доступных устройствах. Здесь отображаются сведения о выбранном оборудовании, его типе, состоянии и месте получения. Эти данные затем используются при создании заявки;
– оформление заявки на выдачу оборудования – процесс, в котором пользователь выбирает оборудование и передаёт данные заявки. После обработки формируется оформленная заявка, а также текущий статус обращения. Информация о выбранном оборудовании передаётся дальше для обработки сотрудником выдачи;
– обработка заявки и возврата оборудования – процесс, выполняемый сотрудником выдачи. В него поступает информация о выдаче и возврате, после чего изменяется статус оборудования. Если устройство возвращено исправным, оно снова может быть доступно для выдачи. При обнаружении проблемы оборудование получает другой статус, а сведения о нём попадают в отчётные данные.
Связи между функциональными блоками показывают последовательность работы приложения. Сначала участник проходит авторизацию. Затем пользователь просматривает оборудование, выбирает подходящий вариант и оформляет заявку. После этого сотрудник выдачи обрабатывает обращение, подтверждает выдачу и фиксирует возврат. При каждом изменении данные об оборудовании и его статусе обновляются.
Администратор участвует в работе системы через управление оборудованием, категориями, пользователями и местами хранения. Также он получает отчёты о заявках и состоянии оборудования. Это нужно для контроля устройств, отслеживания проблемных ситуаций и поддержания актуального реестра.
Функциональная модель IDEF0 показывает, как разрабатываемое веб-приложение работает на уровне основных процессов. Контекстная диаграмма передаёт общий порядок функционирования системы, а декомпозиция раскрывает внутреннюю структуру: авторизацию, управление оборудованием, просмотр устройств, оформление заявки, выдачу, возврат и обновление статусов. Такая модель используется при дальнейшем проектировании базы данных, логики приложения и пользовательского интерфейса.
2.2. Моделирование базы данных
Моделирование базы данных представляет собой процесс разработки структуры хранения данных для разрабатываемой системы. На данном этапе определяется, какие сведения должны храниться в базе, какие объекты участвуют в работе веб-приложения и какие связи существуют между ними.
Для разрабатываемого веб-приложения база данных должна хранить информацию об оборудовании, пользователях, заявках, статусах и местах хранения. Через неё система получает сведения о доступных ноутбуках, планшетах и портативных зарядных устройствах, фиксирует оформление заявки, выдачу оборудования, возврат и изменение состояния устройства.
Цель моделирования базы данных состоит в создании структуры, которая будет удобна для дальнейшей программной реализации [12]. Такая структура должна обеспечивать быстрый поиск нужных сведений, корректное обновление данных после выполнения операций и сохранение истории использования оборудования.
База данных поддерживает основные процессы работы приложения. Пользователь должен иметь возможность зарегистрироваться, войти в систему, просмотреть доступное оборудование, оформить заявку на выдачу, проверить её статус и вернуть устройство после использования. Сотрудник выдачи обрабатывает заявки, подтверждает передачу оборудования, фиксирует возврат и меняет статус устройства. Администратор работает с пользователями, категориями оборудования, местами хранения, заявками и отчётными данными.
При проектировании необходимо учитывать разграничение ролей. Пользователь получает доступ к личному кабинету и своим заявкам. Сотрудник выдачи работает с обращениями и оборудованием, закреплённым за местом хранения. Администратор управляет справочными данными и контролирует состояние системы. Такое разделение должно отражаться в структуре таблиц и связях между ними.
Проектирование базы данных начинается с инфологической модели. В ней описываются основные объекты предметной области: пользователи, роли, оборудование, категории, места хранения, заявки, статусы и история использования. Далее на основе инфологической модели разрабатывается даталогическая модель, где эти объекты получают вид таблиц с атрибутами, первичными ключами и внешними связями.
Инфологическая модель
Инфологическая модель описывает предметную область разрабатываемой системы на логическом уровне. В ней определяется, какие данные нужны веб-приложению для учёта оборудования, оформления заявок, фиксации выдачи и возврата устройств.
На этом этапе внимание уделяется смыслу данных и связям между объектами. Типы полей, ключи таблиц и техническая структура базы данных подробно рассматриваются уже при построении даталогической модели.
В разрабатываемой системе выделяются три основные роли: пользователь, сотрудник выдачи и администратор [6].
Пользователь работает с приложением для получения оборудования, которое может понадобиться во время самоподготовки. После регистрации и входа в систему он просматривает доступные устройства, открывает карточку оборудования, оформляет заявку и следит за её состоянием. После завершения использования пользователь возвращает оборудование, а сведения об операции сохраняются в системе.
К функциям пользователя относятся:
– регистрация в системе– авторизация в системе– просмотр доступного оборудования– просмотр карточки оборудования– оформление заявки на выдачу– выбор типа оборудования– выбор места получения– просмотр статуса заявки– просмотр истории заявок– возврат оборудования– редактирование данных профиля
Сотрудник выдачи подключается к процессу после создания заявки. Он проверяет обращение, подтверждает возможность выдачи, фиксирует передачу устройства пользователю и принимает оборудование обратно. Если после возврата устройство требует проверки или ремонта, сотрудник меняет его статус.
К функциям сотрудника выдачи относятся:
– авторизация в системе– просмотр заявок на выдачу– подтверждение выдачи оборудования– фиксация выдачи оборудования– фиксация возврата оборудования– изменение статуса оборудования– отметка неисправности оборудования– просмотр оборудования по месту хранения
Администратор поддерживает справочные данные и контролирует работу системы. Через административный раздел он управляет пользователями, категориями, оборудованием и местами хранения. Ему также доступны история использования, сведения о состоянии устройств и проблемные ситуации, требующие проверки.
К функциям администратора относятся:
– авторизация в системе– управление пользователями– управление категориями оборудования– управление оборудованием– управление местами хранения– просмотр всех заявок– просмотр истории использования– контроль состояния оборудования– просмотр проблемных ситуаций
Для описания предметной области были выделены следующие сущности: пользователь, роль, категория оборудования, оборудование, место хранения, заявка, статус заявки, статус оборудования, выдача оборудования, возврат оборудования, проблемная ситуация, отчёт и журнал действий.
Данные пользователя нужны для входа в систему, работы с личным кабинетом и оформления заявок. В этой сущности хранятся имя, электронная почта, номер телефона, пароль, роль и состояние учётной записи. Эти сведения связывают пользователя с его заявками и историей использования оборудования.
Роли задают права доступа. Один участник может работать только с личным кабинетом и своими заявками, другой получает доступ к выдаче и возврату, третий управляет справочными данными. Такое разделение требуется, чтобы пользователь не мог изменять сведения о чужих заявках или состоянии оборудования.
Категория оборудования описывает тип устройства. В системе используются ноутбуки, планшеты и портативные зарядные устройства. Если в дальнейшем перечень оборудования расширится, новая категория может быть добавлена без изменения общей логики работы приложения.
Оборудование является центральным объектом реестра. Для каждого устройства фиксируются название, инвентарный номер, категория, описание, место хранения, техническое состояние и текущий статус. По этим данным система определяет, можно ли показать устройство пользователю как доступное для выдачи.
Место хранения помогает понять, где физически находится оборудование. Устройство может быть закреплено за кафедрой, читальным залом, коворкингом, аудиторией самоподготовки или сотрудником выдачи. Одно место хранения может содержать несколько устройств, поэтому между этими объектами формируется связь один-ко-многим.
Заявка связывает пользователя с процессом получения оборудования. В ней сохраняются данные о выбранном типе устройства, месте получения, дате создания, текущем статусе и комментарии. После обработки заявки сотрудником выдачи к ней может быть привязано конкретное оборудование.
Для отслеживания обращения используется статус заявки. Он показывает, на каком этапе находится обращение: создано, ожидает обработки, подтверждено, отклонено, выполнено или завершено после возврата. Благодаря этому пользователь видит текущее состояние своей заявки без обращения к сотруднику.
Статус оборудования отражает уже состояние самого устройства. Оборудование может быть доступно, выдано, возвращено, находиться на проверке или иметь отметку о неисправности. Эти данные особенно важны при просмотре доступного оборудования, поскольку неисправное или уже выданное устройство не должно попадать в список для новой заявки.
Факт передачи устройства фиксируется через сущность выдачи оборудования. В ней сохраняются заявка, пользователь, оборудование, сотрудник выдачи, дата передачи и место получения. Такая запись нужна для истории движения устройства и дальнейшего контроля.
После завершения использования формируется запись о возврате. В ней указываются оборудование, связанная заявка, дата возврата, сотрудник, принявший устройство, состояние после возврата и комментарий. На основании этих данных система обновляет статус оборудования.
Проблемная ситуация появляется, когда обычный сценарий выдачи или возврата нарушается. Например, устройство вернули с неисправностью, статус был указан ошибочно или оборудование не вернули вовремя. Такие записи помогают сотруднику выдачи и администратору разбирать спорные случаи.
Отчёты используются для контроля работы системы. Администратор может получить сведения о заявках, истории использования, состоянии оборудования и проблемных ситуациях. Эти данные помогают оценить, какие устройства используются чаще, какие требуют проверки и где появляются задержки с возвратом.
Журнал действий хранит сведения об операциях, выполненных в системе. В него могут попадать вход пользователя, создание заявки, изменение статуса, выдача, возврат и редактирование справочников. При возникновении ошибки такая история помогает восстановить последовательность действий.
Связи между сущностями строятся вокруг заявки и оборудования. Пользователь может создать несколько заявок, но каждая заявка принадлежит одному пользователю. Оборудование относится к определённой категории и закрепляется за местом хранения. После подтверждения заявки устройство передаётся пользователю, а затем возвращается сотруднику выдачи.
Сотрудник выдачи связан с операциями передачи и возврата оборудования. Его действия меняют состояние заявки и статус устройства. Администратор работает с более широким набором данных: пользователями, категориями, оборудованием, местами хранения, отчётами и проблемными ситуациями.
Инфологическая модель служит основой для дальнейшего построения даталогической модели. Она помогает определить будущие таблицы, связи между ними и состав данных, необходимых для работы веб-приложения по ведению реестра оборудования для самоподготовки студентов ДГТУ.
Даталогическая модель
Даталогическая модель отражает структуру базы данных разрабатываемой системы: таблицы, их атрибуты, ключевые поля и связи. На её основе выполняется физическое хранение данных и обеспечивается доступ к сведениям, которые нужны для работы веб-приложения по ведению реестра оборудования.
База данных разделена на несколько смысловых частей. Одна часть отвечает за учётные записи, роли и уведомления пользователей. Другая связана с оборудованием, его категориями, характеристиками, установленными программами и местами хранения. Отдельные таблицы фиксируют заявки, выдачу, возврат, проблемные ситуации, отчёты и действия пользователей в системе.
На рисунке 3.6 представлена структура данных и взаимосвязи между таблицами.
Рисунок 3.6 – Структура данных и взаимосвязи между таблицами.
Таблица roles содержит сведения о ролях пользователей системы. В поле name хранится название роли, в поле description — её описание. Даты создания и изменения записи фиксируются в полях created_at и updated_at. Первичный ключ таблицы указывается в поле id. Через эту таблицу разграничивается доступ между пользователем, сотрудником выдачи и администратором.
Учётные данные пользователей размещаются в таблице users. В ней хранятся полное имя, адрес электронной почты, номер телефона, пароль, роль и статус учётной записи. Поле role_id связывает пользователя с таблицей roles. Поле email имеет ограничение уникальности, чтобы в системе не появлялись разные учётные записи с одним адресом электронной почты.
Для уведомлений используется таблица notifications. Она связана с пользователем через поле user_id. В таблице сохраняются заголовок уведомления, текст сообщения, признак прочтения и дата создания записи. Такие данные могут использоваться для информирования пользователя о смене статуса заявки, подтверждении выдачи или возврате оборудования.
Категории оборудования вынесены в таблицу equipment_categories. В ней указывается название категории, описание, признак активности, дата создания и дата последнего изменения записи. К категориям могут относиться ноутбуки, планшеты и портативные зарядные устройства. Такое разделение помогает пользователю выбирать оборудование по назначению, а администратору — расширять перечень устройств без перестройки всей базы данных.
Сведения о местах размещения оборудования хранятся в таблице storage_locations. Для каждого места указываются название, тип расположения, корпус, кабинет, описание и признак активности. Местом хранения может быть кафедра, читальный зал, коворкинг, аудитория самоподготовки или зона, закреплённая за сотрудником выдачи.
Текущее состояние оборудования описывается через таблицу equipment_statuses. В ней задаются возможные статусы устройств и их описание. Например, оборудование может быть доступно, выдано, возвращено, находиться на проверке или иметь отметку о неисправности. Отдельная таблица статусов делает структуру базы более гибкой: при необходимости можно добавить новый статус без изменения основной таблицы оборудования.
Основные сведения о реестре размещаются в таблице equipment. Она описывает конкретные единицы оборудования. Для каждого устройства фиксируются название, инвентарный номер, серийный номер, категория, место хранения, техническое состояние, текущий статус и описание. Поле category_id связывает устройство с таблицей equipment_categories, поле storage_location_id — с таблицей storage_locations, а поле status_id — с таблицей equipment_statuses.
Для ноутбуков и планшетов одних общих сведений недостаточно, поэтому в базе предусмотрена таблица equipment_specifications. В ней сохраняются технические характеристики конкретного устройства: процессор, объём оперативной памяти, накопитель, диагональ экрана, операционная система, состояние аккумулятора и дополнительная информация. Эти данные помогают пользователю выбрать устройство под конкретную учебную задачу, например работу с документами, программами или электронными образовательными ресурсами.
С установленными программами связана таблица equipment_software. Она позволяет хранить перечень программного обеспечения для каждого устройства. В таблице указываются название программы, версия, тип лицензии и описание. Такая структура удобна для ноутбуков, поскольку студенту может быть важно заранее узнать, установлен ли на устройстве офисный пакет, браузер, среда разработки, программа для просмотра PDF или другое учебное программное обеспечение.
Для состояний заявок используется таблица request_statuses. Она содержит название статуса и его описание. Эта таблица отделяет состояние заявки от состояния оборудования. Заявка может ожидать обработки, быть подтверждённой, отклонённой, выполненной или завершённой после возврата.
Заявки пользователей на выдачу оборудования хранятся в таблице equipment_requests. Пользователь, создавший заявку, определяется через поле user_id. Категория запрошенного оборудования указывается через category_id, место получения — через storage_location_id. Если заявка уже связана с конкретным устройством, используется поле equipment_id. Статус заявки хранится в поле status_id. Также в таблице предусмотрены комментарий пользователя, дата создания и дата последнего изменения записи.
Факт передачи устройства пользователю фиксируется в таблице equipment_issues. Несмотря на название, в данной модели эта таблица отвечает именно за выдачу оборудования. В ней сохраняются заявка, пользователь, сотрудник выдачи, конкретное оборудование, дата выдачи и место получения. Поле request_id связывает выдачу с заявкой, а поле employee_id показывает, какой сотрудник оформил передачу устройства.
Возврат оборудования отражается в таблице equipment_returns. В ней указываются заявка, запись о выдаче, оборудование, пользователь, сотрудник, принявший устройство, дата возврата, состояние после возврата и комментарий. После добавления такой записи система может обновить статус оборудования и заявки.
Проблемные ситуации связаны с таблицей issues. Обращение может относиться к пользователю, заявке, оборудованию или сотруднику, который обрабатывал выдачу. В таблице указываются тема, описание проблемы, статус обращения, дата создания и дата решения. Для статусов проблемных ситуаций используется отдельная таблица problem_statuses, где хранятся названия возможных состояний обращения и их описание.
Для отчётных данных предусмотрена таблица reports. Она связывается с администратором через поле admin_id. В записи сохраняются тип отчёта, начало и конец отчётного периода, дополнительные параметры и дата формирования. Через эту таблицу можно хранить сведения о сформированных отчётах по заявкам, состоянию оборудования и истории использования.
Журнал действий размещается в таблице activity_logs. Пользователь, выполнивший действие, определяется через поле user_id. В поле action хранится название операции, а в поле description — её описание. Поля entity_type и entity_id позволяют указать, к какому объекту относилось действие: заявке, оборудованию, месту хранения, пользователю или другой записи системы.
Связи между таблицами задаются с помощью внешних ключей. Таблица users связана с roles через поле role_id. Благодаря этому система определяет уровень доступа для каждой учётной записи. Пользователь работает с личным кабинетом и заявками, сотрудник выдачи получает доступ к обработке выдачи и возврата, администратор управляет справочными данными и отчётами.
Оборудование связано сразу с несколькими таблицами. Категория показывает тип устройства, место хранения отражает его физическое расположение, статус определяет текущее состояние. Дополнительные таблицы equipment_specifications и equipment_software расширяют описание оборудования, когда речь идёт о ноутбуках или планшетах. За счёт этого реестр хранит не только факт наличия устройства, но и сведения, полезные для выбора оборудования перед заявкой.
Заявка связывает пользователя с выбранной категорией оборудования и местом получения. После обработки заявки сотрудником выдачи к ней может быть привязано конкретное устройство. Такой подход удобен, если пользователь сначала выбирает только тип оборудования, а сотрудник уже подбирает свободную единицу из реестра.
Выдача оборудования зависит от заявки и конкретного устройства. Запись в таблице equipment_issues показывает, кто получил оборудование, какое устройство было передано и какой сотрудник оформил выдачу. После этого статус оборудования меняется на выданное.
Возврат связан с уже оформленной выдачей и оборудованием. После сохранения записи в таблице equipment_returns система обновляет статус устройства. Если оборудование вернули без замечаний, оно снова может стать доступным. При обнаружении неисправности устройство переводится в состояние проверки или неисправности.
Проблемные ситуации могут относиться к разным объектам системы. Чаще всего они связываются с пользователем, заявкой или оборудованием. Такая связь помогает администратору быстрее найти нужные сведения и восстановить ход операции.
В разрабатываемой системе предусмотрено несколько уровней доступа. Пользователь регистрируется, входит в личный кабинет, просматривает оборудование, изучает характеристики и установленное программное обеспечение, оформляет заявку, отслеживает её статус, возвращает устройство и редактирует профиль. Сотрудник выдачи работает с заявками, выдачей, возвратом и статусами оборудования. Администратор управляет пользователями, категориями, оборудованием, местами хранения, отчётами и проблемными ситуациями.
Разработанная даталогическая модель описывает хранение данных, необходимых для работы веб-приложения по ведению реестра оборудования. В ней отражены учётные записи, роли, уведомления, категории, оборудование, характеристики устройств, установленное программное обеспечение, места хранения, заявки, выдача, возврат, проблемные ситуации, отчёты и журнал действий. Такая структура поддерживает основные процессы системы и сохраняет историю использования оборудования.
3. Программная реализация веб-приложения аренды зарядных устройств
3.1 Архитектура веб-приложения аренды зарядных устройств
Архитектура разрабатываемой системы построена на взаимодействии пользовательского интерфейса, административной панели, серверной части, базы данных и внешних сервисов [13]. Такая структура позволяет разделить основные функции системы и упростить обработку данных, связанных с пользователями, станциями, повербанками и оплатой.
Рисунок 4.1 – Архитектура веб-приложения аренды зарядных устройств
Пользовательский интерфейс реализован с помощью Blade-шаблоновLaravelиBootstrap [11]. Через него пользователь может пройти регистрацию, выполнить вход в систему, просмотреть доступные станции, получить сведения о повербанках и работать с личными данными.
Серверная часть также разработана на фреймворке Laravel. Она принимает запросы от интерфейса, проверяет ведённые данные, выполняет основную логику приложения и обращается к базе данных. Через серверную часть происходит связь между страницами веб-приложения, хранилищем данных и подключенными сервисами.
Для хранения информации используется база данных MySQL. В ней размещаются сведения о пользователях, ролях, станциях, повербанках, тарифах, платежах, и других объектах системы. Файловая система применяется для хранения изображения,QR-кодов и служебных файлов [6].
Веб-приложение размещается на удалённом сервере, именно на нём находятся файлы проекта, база данных и необходимые компоненты для работы сайта. За счёт этого доступ к системе может выполняться через браузер с разных устройств.
Работа системы строится по следующему принципу: пользователь или администратора выполняет действие через интерфейс, сервер Laravel обрабатывает запрос, обращается к базе MySQL и возвращает результат на страницу веб-приложения. Такая архитектура подходит для реализации системы аренды зарядных устройств и обеспечивает понятную структуру работы приложения.

3.3 Реализация базы данных
База данных разрабатываемой системы реализована на MySQL. Она размещается на удалённом сервере с файлами проекта и используется серверною частью Laravel для хранения и обработки сведений, необходимых для работ системы.
Рисунок 4.2 – Миграции базы данных
Структура база создаётся через миграции Laravel. В миграциях описаны таблицы, поля, типы данных, ключи и связи. После запуска миграций Laravelформирует нужную структуру в MySQL [15]. Такой способ удобен при переносе проекта на сервер, потому что база создаётся из файлов приложения без ручного добавления каждой таблицы через панель управления.
Структура базы данных создаётся через миграции Laravel. В таких файлах задаются таблицы, поля, типы данных, ключи и связи. После выполнения миграций Laravel создаёт нужную структуру в MySQL [15]. При переносе проекта на сервер это упрощает подготовку базы: разработчику не приходится вручную добавлять каждую таблицу через панель управления.
Обращение приложения к базе данных выполняется через модели Laravel. Пользователь или администратор открывает страницу, заполняет форму либо выбирает действие в интерфейсе. После этого запрос передаётся в серверную часть. Laravel принимает данные, обращается к нужной модели и выполняет операцию в базе данных: получает запись, добавляет сведения, изменяет данные или удаляет их.
Для связи таблиц используются внешние ключи. Они закрепляют данные за нужными объектами системы [8]. Например, пользователь относится к определённой роли, повербанк связан со станцией и слотом, платёж прикрепляется к конкретной операции. Такая структура снижает риск разрозненного хранения сведений и помогает быстрее получать нужные данные при работе приложения.
При авторизации приложение обращается к таблице пользователей, проверяет введённые данные и определяет роль учётной записи. После успешного входа пользователь переходит в свою часть сайта. Администратор получает доступ к панели управления [2]. В административной части сведения из базы выводятся в виде списков и форм. Через них можно просматривать записи, редактировать данные и менять состояние объектов системы.
База данных участвует во всех основных действиях веб-приложения. Через неё сохраняются данные пользователей, сведения о станциях, информация о повербанках, платежахи служебных действиях. При изменении данных через интерфейсLaravel передаёт изменения в MySQL, после чего обновлённая информация снова отображается на страницах сайта
Размещение базы данных на сервере позволяет использовать её вместе с опубликованным веб-приложением [21]. Файлы проекта, настройки подключения и база данных находятся в одной серверной среде, поэтому Laravelможет напрямую обращаться к MySQL при выполнении запросов. Это обеспечивает нормальную работу сайта через браузер и позволяет использовать систему с разных устройств.

Такой вариант оформления позволяет пользователю быстро переходить между основными страницами сервиса.

Главная страница знакомит пользователя с назначением системы. В центральной части размещён крупный информационный блок с описанием сервиса аренды повербанков на территории учебного корпуса. Рядом находится изображение выдачи. Ниже отображается краткие показатели: количество станций, число слотов, режим оплаты и контроль работы системы [1]. В разделе истории отображаются ранее созданные записи об аренде. Данные представлены в виде таблицы. Для каждой записи указывается номер операции, повербанк, станция выдачи, дата начала, статус и сумма. Такая страница помогает пользователю отслеживать выполненные действия в системе.
Рисунок 4.8 – Страница банковских карт.
Раздел банковских карт используется для привязки платёжных данных. В форме пользователь вводит номер карты, после чего система сохраняет последние четыре цифры и служебный платёжный токен. Справа выводится список добавленных карт. Такой подход позволяет показать факт привязки карты без хранения полного номера в открытом виде.
Рисунок 4.9 – Страница платежей
В разделе платежей отображается история операций по оплате. Таблица содержит номер платежа, связанную аренду, способ оплаты, статус, сумму и дату выполнения операции. В представленном варианте используется демонстрационная оплата, поэтому система показывает результат операции без подключения реального банка.
Рисунок 4.10 – Страница создания обращения
Страница обращения, предназначенная для сообщения о проблемной ситуации. Пользователь выбирает тип проблемы, при необходимости указывает аренду, станцию или повербанк [6]. Основная часть формы отведена под описание ситуации. После отправки обращения становится доступным для просмотра в системе администрирования.
Рисунок 4.11 – Страница уведомлений
Раздел уведомлений сообщает пользователю сообщает о важны событиях. На странице отображается название уведомления, текст сообщения, дата создания и отметка о прочтении. В примере показано уведомление о завершении аренды и сумме оплаты. Пользователь может отметить сообщения прочитанными.
Веб страницы веб-приложения выполнены в едином стиле. Боковая панель сохраняется во всех разделах, поэтому переход между страницами остаётся понятным [11]. Кнопки, карточки, таблицы и формы имеют одинаковое оформление. Это делает работу с сервисом удобной для пользователя и упрощает дальнейшее развитие интерфейса.
4.1 Административный интерфейс
Административная часть веб-приложения предназначена для контроля работы сервиса повербанков. Доступ к ней получает пользователь с ролью администратора после авторизации. В этом разделе собраны страницы, через которые можно следить за состоянием станций,просматривать пользователей, управлять повербанками, проверять аренды, возвраты, обращение и отчёты.
Рисунок 4.12 – Панель администратора
Панель администратора служит основной страницей контроля сервиса. В верхней части отображаются общие показатели: количество пользователей, станций, повербанков, активных аренд, оплаченных операций и проблемных ситуаций [16]. Ниже размещены последние аренды, состояние станций, статусы повербанков и журнал действий. Эта страница позволяет быстро оценить текущее состояние системы.
Рисунок 4.13 – Страница пользователей
Раздел пользователей содержит список зарегистрированных учётных записей. В таблице отображаются ФИО, электронная почта, телефон, роль и статус пользователя [20]. Для каждой записи доступно изменение данных. Этот раздел используется для просмотра пользователей сервиса и контроля их доступа к системе.
Рисунок 4.14 – Страница станций в административной панели
Страница станций предназначена для управления точками выдачи и возврата повербанков. В таблице выводится название станции, её расположение,QR-код, количество слотов, число размещённых повербанков и текущий статус [11]. Администратор может открыть список слотов, изменить сведения о станции или удалить запись. Отдельная кнопка позволяет добавить новую станцию.
Рисунок 4.15 – Страница повербанков
Раздел повербанков показывает устройства, зарегистрированные в системе. Для каждого повербанка отображается серийный номер, станция размещения, слот, уровень заряда, статус и техническое состояние. Через кнопки управления администратор может изменить данные устройства или удалить его из системы.
Рисунок 4.16 – Страница тарифов
Страница тарифов используется для настройки стоимости аренды. В форме создания нового тарифа указывается название, цены за 30 минут, час, сутки и описание. Уже созданные тарифы отображаются в отдельном блоке. Их можно редактировать, отключать или удалять[6]. Эти данные применяются при расчёте стоимости использования повербанка.
Рисунок 4.17 – Страница всех аренда
Раздел всех аренд содержит сведения об операциях пользователей. В таблице указывается номер аренды, пользователь, повербанк, станция выдачи, станция возврата, статус и сумма [6]. По этим данным администратор может проверить активные и завершённые аренды.
Рисунок 4.18 – Страница возвратов
Страница возвратов фиксирует завершённые операции по возврату устройств. В таблице отображается номер аренды, пользователь, повербанк, станция, слот, дата и статус возврата. Этот раздел помогает проверить, куда был возвращён повербанк и корректно ли завершилась операция.
Рисунок 4.19 – Страница проблемных ситуаций
Раздел проблемных ситуаций предназначен для обработки обращений пользователей. В таблице предусмотрены данные о пользователе, типе проблемы, описании, связанных объектах и статусе [3]. При отсутствии обращений система выводит сообщение, что новых записей нет.
Рисунок 4.20 – Страница отчётов
Страница отчётов позволяет сформировать сводку за выбранный период. Администратор выбирает тип отчёта, дату начала и дату окончания. Справа отображаются созданные отчёты с указанием периода, администратора и даты создания [2]. Ниже выводится краткая сводка по данным системы.
Рисунок 4.21– Журнал действий
Журнал действий хранит сведения о событиях, выполненных в системе. В таблице отображается дата, пользователь, действие и описание операции. Здесь фиксируются вход в систему, выход, создание аренды, возврат повербанка и создание обращения. Такой раздел помогает контролировать работу приложения и разбирать возможные ошибки.
Административный интерфейс дополняет пользовательскую часть веб-приложения [4].Через него выполняется обслуживание системы, обновление данных и контроль состояния сервиса. Единое оформление страниц делает работу администратора более понятной и ускоряет переход между основными разделами.
Заключение
В рамках выполнения дипломной работы был проведён анализ предметной области, связанной с арендой портативных зарядных устройств на территории института. Были рассмотрены существующие решения, применяемые для краткосрочной аренды повербанков в общественных пространствах. Изучение подобных сервисов показало, что большинство из них рассчитано на широкую городскую среду и слабо учитывает особенности учебного заведения. Для института важны быстрый доступ к устройству, понятный порядок аренды, контроль возврата и удобное управление станциями выдачи. Это подтвердило необходимость разработки собственной системы, ориентированной на использование внутри образовательной организации.
На основе проведённого анализа была спроектирована информационная система аренды повербанков. Для описания структуры и логики работы разработаны функциональные модели IDEF0, диаграммы потоков данных DFD, даталогическая модель базы данных и диаграмма прецедентов. Эти материалы позволили заранее определить основные процессы системы, состав участников, направления передачи данных и порядок взаимодействия пользователя с веб-приложением.
Обоснован выбор средств разработки. Для создания пользовательской части применены HTML5 и CSS3. Динамическое поведение интерфейса реализовано с использованием JavaScript, за счёт чего выполняется обновление отдельных элементов страницы без полной перезагрузки. Серверная часть разработана на PHP [19]. Для хранения данных выбрана СУБД MySQL [20], управление базой данных выполнялось через phpMyAdmin[21].Адаптивность страниц обеспечена с помощью медиа-запросов и современных средств построения сетки интерфейса. Разработка велась в среде Visual Studio Code [24], локальная проверка работы системы проводилась на Open Server Panel.
В ходе программной реализации создана информационная система, включающая следующий функционал:
регистрация и авторизация пользователей с разграничением прав доступа;
просмотр доступных станций выдачи повербанков;
просмотр информации о наличии свободных устройств;
оформление аренды повербанка через веб-интерфейс;
привязка банковской карты и оплата аренды;
просмотр текущей аренды пользователем;
возврат повербанка в станцию;
личный кабинет пользователя с данными профиля и историей аренд;
административная панель для управления пользователями;
управление станциями выдачи и повербанками;
просмотр сведений о текущих арендах и оплатах.
Разработанная система хранит данные о пользователях, станциях, повербанках, арендах и платежах в единой базе данных. Для входа в систему используется логин и пароль. Права доступа разделены по ролям: пользователь оформляет аренду, просматривает доступные устройства и контролирует свои активные операции, администратор управляет пользователями, станциями, повербанками и сведениями об арендах.
Разработанная информационная система автоматизирует основные процессы аренды портативных зарядных устройств: от авторизации пользователя до возврата повербанка в станцию. Внедрение такого решения позволит упростить получение устройства в течение учебного дня, сократить время обслуживания пользователей, обеспечить контроль состояния повербанков и снизить нагрузку на сотрудников, отвечающих за организацию выдачи оборудования.

$user = User::create($request->safe()->merge([

'status' => 'active',
])->all());
Auth::login($user);
$request->session()->regenerate();
ActivityLog::record($user->id, 'register', 'Регистрацияновогопользователя');
returnredirect()->route('dashboard');
}

Листинг A.11 – Модель «Расчет стоимости аренды»
public function calculatePrice(?CarbonInterface $until = null): float
{
$until ??= now();
$minutes = max(1, $this->started_at->diffInMinutes($until));
$tariff = $this->tariff;
if ($minutes <= 30) {
return (float) $tariff->price_per_30_min;
}
if ($minutes <= 60) {
return (float) $tariff->price_per_hour;
}
$days = (int) ceil($minutes / 1440);
return $days * (float) $tariff->price_per_day;
}

Листинг A.19 – Методы контроллера администратора «Синхронизация слотов пауэрбанка»
private function normalizedData(array $data): array
{
$data['station_id'] = $data['station_id'] ?: null;
$data['slot_id'] = $data['slot_id'] ?: null;
if ($data['slot_id']) {
$slot = StationSlot::findOrFail($data['slot_id']);
if ((int) $slot->station_id !== (int) $data['station_id']) {
thrownew \RuntimeException('Выбранныйслотнепринадлежитвыбраннойстанции.');
}
}
if ($data['status'] === 'rented') {
$data['slot_id'] = null;
}
return $data;
}
private function syncSlotStatuses(?int $oldSlotId, Powerbank $powerbank): void
{
if ($oldSlotId && $oldSlotId !== $powerbank->slot_id) {
StationSlot::whereKey($oldSlotId)->update(['status' => 'empty']);
}
if ($powerbank->slot_id) {
StationSlot::whereKey($powerbank->slot_id)->update(['status' => 'occupied']);
}
}
